## Why Performance Matters for i18n

Traditional i18n libraries ship an ICU MessageFormat parser to the browser. On every render, the parser must tokenize the message string, build an AST, resolve plurals and selects, then interpolate values. This work is repeated for every message, every time the component re-renders.

Fluenti takes a fundamentally different approach: **parsing and compilation happen at build time**. By the time your app reaches the browser, messages are either static strings or tiny pre-compiled functions. The runtime cost is reduced to a hash-map lookup and a function call — orders of magnitude faster than re-parsing ICU syntax on every render.

The benchmarks below quantify both the build-time and runtime performance characteristics.

## Build-Time Performance

Build-time operations run once during `pnpm build` or in watch mode. They do not affect end-user experience, but faster builds mean a tighter feedback loop during development.

### Parser Throughput

The parser converts ICU MessageFormat strings into an AST. Throughput depends on message complexity.

| Message type | ops/sec | Mean (ms) |
|---|---:|---:|
| Plain text | 8,227,585 | 0.0001 |
| Single variable (`{name}`) | 3,824,414 | 0.0003 |
| Multi variable (`{x} + {y} = {result}`) | 1,910,671 | 0.0005 |
| Plural (simple, 2 forms) | 910,203 | 0.0011 |
| Plural (6 forms / Arabic) | 482,835 | 0.0021 |
| Plural + offset | 574,233 | 0.0017 |
| Select | 748,296 | 0.0013 |
| Nested plural + select | 240,351 | 0.0042 |
| Function — `{amount, number}` | 2,017,934 | 0.0005 |
| Function — `{date, date}` | 2,209,899 | 0.0005 |
| Escaped quotes | 3,386,641 | 0.0003 |
| Long message (~500 chars) | 146,617 | 0.0068 |

Even the most complex messages (nested plural + select) parse at **240k ops/sec** — fast enough to process an entire application's message catalog in milliseconds.

### Compilation Speed

All message types compile at roughly **20M ops/sec**. The compiler produces static strings when possible (no variables), avoiding function overhead entirely.

## Runtime Performance

Runtime operations happen in the browser (or on the server during SSR). These are the numbers that directly affect your users.

### Interpolation

The interpolation engine uses an LRU cache to avoid re-parsing messages that have already been seen.

**Cache hit (warm path):**

| Message type | ops/sec | Mean (ms) |
|---|---:|---:|
| Static text | 5,364,131 | 0.0002 |
| Single variable | 4,600,859 | 0.0002 |
| Plural | 1,139,161 | 0.0009 |
| Select | 3,057,930 | 0.0003 |

**Cache miss (cold path):**

| Scenario | ops/sec | Mean (ms) |
|---|---:|---:|
| Unique message (cold) | 838,143 | 0.0012 |
| Batch 100 cold messages | 26,324 | 0.038 |
| 501 messages (LRU eviction) | 1,793 | 0.56 |

Even on a cache miss, a single message interpolates in **1.2 microseconds**. The LRU cache (max 500 entries) ensures that hot messages stay fast.

### Catalog Lookup

Message lookup from the catalog is a direct property access on a null-prototype object. Performance is stable regardless of catalog size.

| Catalog size | get (first) | get (middle) | get (last) | has (existing) | has (missing) |
|---|---:|---:|---:|---:|---:|
| 100 messages | 14.6M | 10.9M | 10.2M | 14.1M | 14.2M |
| 1,000 messages | 10.6M | 10.3M | 10.4M | 13.8M | 14.0M |
| 10,000 messages | 19.3M | 17.9M | 18.7M | 20.1M | 19.0M |

*All values in ops/sec.*

Lookups consistently achieve **10M+ ops/sec** even with 10,000 messages. Catalog size has negligible impact on lookup speed.

## Compile-Time vs Runtime Parsing

The key architectural advantage of Fluenti is the separation of parsing from rendering:

| Approach | What happens at runtime | Cost per render |
|---|---|---|
| **Traditional i18n** (vue-i18n, react-intl, etc.) | Parse ICU string, build AST, resolve plurals, interpolate values | Full parse + interpolation |
| **Fluenti (compile-time)** | Hash-map lookup + function call | Lookup + function call |

For a message like `{count, plural, one {# item} other {# items}}`:

- **Traditional**: Parse the ICU string (~910k ops/sec), resolve plural rules, then interpolate — every time the component renders.
- **Fluenti**: The message was already compiled to a function during build. At runtime, it is a direct property lookup (~10M+ ops/sec) and a single function call (~1M+ ops/sec for plurals).

The result: Fluenti's runtime path is **5--10x faster** than parsing ICU on every render, and the gap widens with message complexity. For nested plural + select messages, the speedup can exceed **40x** compared to cold-parsing the same ICU string.
